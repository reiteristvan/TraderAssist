<objective>
Persist four entry-time signal features — `rsi_entry`, `rvol`, `pullback_depth_pct`, `pct_to_52w_high` — as columns on the `signals` table, written by BOTH the backtest ingest path and the live scan path through ONE shared normalization helper.

These values are already computed and already flow through `backtest.py` → `simulate.Signal` → `report.py`, but `store_db.py` never writes them and no column exists, so they live only inside a fresh backtest run's memory and vanish on write. `gate_detail_json` is NULL for every backtest row, so there is no fallback source — the data is genuinely unqueryable today.

Purpose: a train/holdout winner-loser analysis over run `4f4fe68_2021-01-01_20260702_090418` (3,813 qualified resolved trades) could only test `score`, `confidence`, `atr_pct`, `close`, `target_r`, `target_atr`, `industry_momentum`, `industry_rank_pct` — none separated winners from losers out of sample. The four features most likely to separate were untestable. This unblocks that.
Output: one shared helper, one schema version bump (9 → 10, additive), four columns wired through both insert functions and both write paths, and tests pinning the semantics. No gate, score, or confidence change. No backfill.
</objective>

- **D-03 — `pct_to_52w_high` is stored as percent distance BELOW the 52-week high** (higher = further below) for both strategies and both sources. `BreakoutResult.pct_to_52w_high` is the OPPOSITE convention (`close / high_52w * 100`, higher = closer) and MUST be converted via `100.0 - raw`. This is the highest-risk aspect of the task: writing the raw breakout value through would put a "closeness" number and a "distance" number in the same column, and any pooled query mixing sources would be silently wrong rather than erroring.

Out of scope (do not start): re-running the backtest, backfilling the four columns for existing rows, surfacing the fields in the web API or UI, any change to `report.py` (it already consumes these fields in memory).

<prior_investigation>
Measured during planning against the working tree. Treat as established; re-verify only if a task fails.

1. **No circular import from placing the helper in `scanner/core.py` — CONFIRMED SAFE.** `core.py`'s module-level imports are stdlib plus `pandas` and `yfinance` only; it imports neither `scanner.backtest` nor `scanner.simulate` anywhere. `backtest.py` already imports six names from `core.py`. The one constraint: `scanner/strategies/pullback.py` and `scanner/strategies/breakout.py` both import FROM `scanner.core`, so the helper must import `BreakoutResult` lazily inside the function body — which is the pattern `core.py` already uses at line 675 and `backtest.py` at lines 394-395.

2. **`precomp_t` is never None on the line that matters.** `precomp_by_ticker[ticker] = _precompute_bars(...)` is assigned unconditionally for every ticker in `bars_by_ticker` (backtest.py:294), and the inner loop only reaches line 363 for tickers in that dict. So the current `elif precomp_t is not None` guards are unreachable-as-False in practice, and the helper's "compute from the frame when the precomputed scalar is absent" fallback introduces no backtest behavior change. State this in the SUMMARY.

3. **THE COLLISION — `run_scan` builds `row = asdict(result)`, which already contains keys named `pullback_depth_pct` and `pct_to_52w_high`.** For a BreakoutResult, `row["pct_to_52w_high"]` holds the raw closeness value (e.g. 99.51). Writing the normalized distance value back into that same key would silently flip the meaning of a column that already flows into `combined.to_csv(args.csv)`. The four normalized values MUST therefore go into namespaced keys (`entry_*`) in the live row dict. This is a distinct instance of the same trap D-03 names.

4. **`_print_scan_results` uses an explicit column allowlist** (`scan.py:196-200`), so four extra DataFrame columns cannot disturb terminal output. `combined.to_csv()` will gain four columns — additive and acceptable.

5. **NaN reaches the live write path via pandas, not via the helper.** `scan.py:155` concatenates the per-strategy frames and `scan.py:169` calls `.to_dict("records")`; a column that is None for one strategy and float for the other becomes float64 with NaN. SQLite does coerce a NaN bind to NULL, but relying on that is fragile — coerce NaN to None explicitly at the journal boundary. Assigning all four `entry_*` keys on EVERY row (both strategies) also keeps concat from inventing columns.

6. **The web layer needs NO change — but assert it.** `web/api/db/index.js` runs `SELECT * FROM signals` (lines 131, 139, 171, 205, 293) with no strict schema validator; extra columns pass straight through as extra JSON keys. Its `_applyMigrations` (lines 69-75) is guarded on the presence of the `notes` column, so against a v10 DB it is a no-op and can never downgrade `schema_version`. The API's own test fixtures build their own tmp DBs with explicit CREATE TABLE and never reference the new column names.

7. **The golden-master path is unreachable.** `tests/test_golden_master.py` calls `pb.evaluate()` / `br.evaluate()` directly and asserts gate/score fields only. This task touches neither strategy module. `tests/golden/breakout_qualifying.json` records `pct_to_52w_high: 99.51` — the native closeness form — which makes it a convenient numeric anchor for the D-03 conversion test (99.51 → 0.49), not a fixture at risk.

8. **`tests/test_store_db.py::_sample_signal` omits the optional keys.** `insert_signal` / `insert_signals_batch` survive that today only because they merge `sig.get("...")` defaults over `**sig`. The four new columns must follow the identical `sig.get(...)` pattern or existing tests will raise on a missing named parameter.

9. **Breakout `vol_ratio` can legitimately be `0.0`** (`breakout.py:108` yields `0.0` when the SMA50 volume is falsy). The current inline block passes that `0.0` straight into `Signal.rvol`. Preserve that — do not coerce `0.0` to None, or the extraction stops being behavior-preserving.
</prior_investigation>
