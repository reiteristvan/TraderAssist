<objective>
Restore the web API's database connectivity, broken by today's Node 22 -> 24 upgrade, and
stop `getDb()` from swallowing the cause.

`better-sqlite3` is the only native module in `web/api`. Its 11.10.0 binary is compiled
against NODE_MODULE_VERSION 127 (Node 22); the runtime is now Node 24.19.0 / ABI 137.
The constructor throws, `getDb()` catches it into `catch (_err) { return null }`, and every
route reports `503 {"error":"Database unavailable"}` — blaming the data for a loader fault.
The database itself is healthy (schema v10, 263,544 signals, 52 runs, integrity_check ok).

Locked decisions from CONTEXT.md (aliases for the coverage gate: D-01 = D1, D-02 = D2,
D-03 = D3):
- **D1 / D-01** — Bump `web/api/package.json` `better-sqlite3` from `^11.10.0` to `^12.6.2`
  and reinstall so a prebuilt ABI-137 binary lands. `npm rebuild` is NOT an option: this
  machine has no Visual Studio C++ build tools, and Node 24 prebuilds only begin at 12.2.0,
  so the pinned `^11.10.0` range can never resolve to one.
- **D2 / D-02** — `getDb()` and `getWriteDb()` must log the caught error before returning
  `null`, so the next loader failure is not misreported as a data failure. They still return
  `null`; the 503 contract is unchanged.
- **D3 / D-03** — Both fixes in one task, as two separate atomic commits.

Purpose: the API has been dark for a day because a driver fault was rendered as a data
fault. Fixing the driver restores service; fixing the diagnostics is what stops the next
occurrence from costing another day.

Output: a working ABI-137 better-sqlite3 install, a regenerated lockfile, a logging helper
in `web/api/db/index.js`, and a jest module proving both the loud and the quiet paths.
</objective>

1. **The addon load is lazy.** With the currently-broken 11.10.0 install,
   `require('better-sqlite3')` SUCCEEDS; the failure lands in the `new Database(...)`
   constructor, i.e. precisely inside the existing catch block. The diagnostics fix will
   therefore capture the real ABI error.

2. **The thrown error's `.code` is `undefined`** for this failure. The message carries the
   payload: a multi-line `Could not locate the bindings file. Tried: ...` listing, with the
   dlopen failure embedded. So the log must surface `err.message` / the error object —
   logging only `err.code` would emit nothing useful.

3. **A clean, deterministic trigger for the genuine-open-failure path exists:** point
   `DB_PATH` at an existing DIRECTORY. `fs.existsSync(dir)` returns true, so the guard is
   passed, and the constructor throws `SQLITE_CANTOPEN_ISDIR`. Verified under
   better-sqlite3 12.6.2 on Node 24.19.0. This is the recommended test trigger.

4. **Do NOT use a garbage-bytes file as the trigger.** A file containing non-SQLite bytes
   does NOT throw from the constructor — `SQLITE_NOTADB` only surfaces at the first query,
   so it would never reach the catch block being tested.

5. **12.6.2 reads production data correctly.** Installed in a scratch directory and opened
   `D:/Projects/TraderAssist/data/scanner.db` read-only: `schema_version` = 10, signals =
   263544, runs = 52, `integrity_check` = ok. Exactly the CONTEXT.md figures.

6. **Environment:** Node v24.19.0, `process.versions.modules` = 137, npm 11.5.2.

7. **`node_modules/` is already ignored** via `web/api/.gitignore` line 1. No .gitignore
   change is needed and none should be made.

8. **`getWriteDb` is not exported** from `web/api/db/index.js`. Exercise its failure path

data — that misattribution is the entire reason this task exists.
